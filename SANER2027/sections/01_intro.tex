\section{Introduction}
\label{sec:01_intro}
\fixed{Users and contributors of software projects report bugs, request features, and ask questions through issue trackers such as GitHub Issues~\cite{colavito2024leveraging}. Labeling each issue report with its type speeds up its resolution~\cite{liao2018exploring} and supports issue prioritization~\cite{catolino2019not}, issue assignment~\cite{wu2022spatial}, and developer onboarding~\cite{santos2023tag, aracena2025applying}. Yet labels are rarely used~\cite{kallis2019ticket} and often wrong~\cite{antoniol2008bug, herzig2013s}, and manually assigning them is laborious~\cite{fan2017road}. To address these problems, many studies propose methods for automated issue report classification (\irc) and typically evaluate them on the labels \emph{bug}, \emph{feature}, and \emph{question}~\cite{kallis2019ticket, izadi2022catiss, kallis2024nlbse, colavito2025benchmarking, heo2025study}.}

\fixed{Most \irc\ methods learn from labeled issues. Early work trained classic machine-learning classifiers~\cite{antoniol2008bug, kallis2019ticket, pandey2017automated}, later work fine-tuned pre-trained transformer models~\cite{izadi2022catiss, trautsch2022predicting, colavito2022issue, wang2021well}, and recent work applies large language models (LLMs)~\cite{colavito2025benchmarking, aracena2025applying, heo2025study}. Among LLM-based methods, fine-tuning on labeled issues gives the best reported results~\cite{heo2025study, aracena2025applying, aracena2024applyinglargelanguagemodels}, with Low-Rank Adaptation (LoRA~\cite{hu2022lora}) for open models. Fine-tuning, however, adds a training run that must be repeated to learn from newly labeled issues or to adopt a newer model~\cite{fan2017road, kallis2019ticket}.}

\fixed{LLMs can also use labeled issues without training. Through in-context learning, a model infers a task from a few labeled examples in its prompt~\cite{brown2020language}, and choosing the labeled examples most similar to the query issue can outperform choosing them at random~\cite{liu2022makes, yu2023retrieval}. With such retrieval-augmented few-shot prompting, a newly labeled issue only needs to be indexed, and the LLM can be replaced without retraining. For future work, Heo and Lee~\cite{heo2025study} suggest few-shot prompting, and Aracena et~al.~\cite{aracena2025applying} suggest retrieval augmentation to reduce the need for extensive fine-tuning and to help with ambiguous labels such as question. To our knowledge, however, retrieval-augmented few-shot prompting has not been systematically evaluated for \irc\ or compared with LoRA fine-tuning.}

\fixed{This paper does both. In an empirical study, we use four Qwen2.5-Instruct models of 3B to 32B parameters~\cite{yang2024qwen25} and Heo and Lee's balanced benchmark of issue reports from eleven projects~\cite{heo2025study}, each with 300 labeled and 300 test issues. Following Heo and Lee, the retrieval index and the fine-tuning data come either from the target project's 300 labeled issues alone (the project-specific setting) or from all 3{,}300 labeled issues of the eleven projects (the project-agnostic setting).}

\fixed{The retrieved examples are the labeled issues most similar to the query, so we first test how well their labels alone predict the query's label. \textbf{Vo}ting-based \textbf{TAG}ging (\votag) labels the query by a similarity-weighted vote over these neighbors, without an LLM. Using only the target project's labeled issues, it reaches 0.595 macro~$F_1$, so the neighbors carry label information that an LLM could use. \textbf{R}etrieval-\textbf{A}ugmented \textbf{G}enerative \textbf{TAG}ging (\ragtag) therefore shows these neighbors to the LLM as examples. As with prior \irc\ methods~\cite{colavito2024impact, colavito2025benchmarking}, \ragtag's most frequent error is labeling questions as bugs, and \textbf{B}alanced \ragtag\ (\bragtag) targets this error by removing the bug-labeled examples for suspected questions.}

\fixed{In this study, we answer four research questions.}

\myparagraph{\fixed{RQ1}} \fixed{\emph{How effectively can retrieval alone classify issue reports, and at what point does adding more retrieved neighbors stop helping?} \votag\ peaks at 0.595 macro $F_1$ with 15 neighbors from the target project and at 0.604 with 16 neighbors from all eleven projects. It is weakest on questions and labels 32\% of them as bugs.}

\myparagraph{\fixed{RQ2}} \fixed{\emph{How well does retrieval-augmented few-shot prompting classify issue reports, and how does performance vary with the number of in-context examples?} \ragtag\ shows the LLM $k$ examples, for seven values of $k$ from 0 (zero-shot prompting) up to 15, the bound set by \votag's peaks. Every configuration with at least one example outperforms both zero-shot prompting and \votag's best result. At each model's best $k$, \ragtag\ reaches 0.697--0.767 macro $F_1$ with the target project's labeled issues. Retrieved examples lower the share of questions predicted as bugs from 46--59\% at zero-shot to 26--36\% at the best $k$, but question remains the weakest class.}

\myparagraph{\fixed{RQ3}} \fixed{\emph{Can a balanced retrieval intervention reduce question-to-bug misclassification and improve retrieval-augmented few-shot performance?} The models label many questions as bugs even without examples, so we hypothesize that bug-labeled neighbors retrieved for a question reinforce this error. \bragtag\ therefore removes the bug-labeled examples from the prompt, unless they outnumber the question-labeled ones by more than a small margin. It scores higher than \ragtag\ at every $k{\ge}6$ for all four models, and by 0.015--0.024 macro $F_1$ at each method's best $k$ (95\% confidence intervals exclude zero). It also lowers the share of questions predicted as bugs to 19--27\%, at the cost of bug recall.}

\myparagraph{\fixed{RQ4}} \fixed{\emph{How do retrieval-based methods compare with LoRA fine-tuning in classification performance, peak GPU memory, and labeled-data needs?} With the same 300 labeled issues of the target project, \ragtag\ and \bragtag\ at their best $k$ score higher than LoRA fine-tuning at every model size, by 0.021--0.060 macro~$F_1$. When fine-tuning instead uses all 3{,}300 labeled issues of the eleven projects, \ragtag\ trails it by 0.028 macro~$F_1$ on average over the four model sizes, and \bragtag\ trails it by 0.010, a difference that is not statistically significant. Once a \votag\ fallback replaces invalid LLM outputs, \bragtag\ matches fine-tuning (+0.001 macro~$F_1$ on average). Beyond macro~$F_1$, fine-tuning finds more of the actual bugs but over-predicts the bug label, whereas \bragtag\ makes fewer false bug predictions at most model sizes. The question-to-bug confusion persists under every method we test, including fine-tuning. Both retrieval-based methods need no training, 300 instead of 3{,}300 labeled issues, and 33\% less peak GPU memory than fine-tuning on average.}

\fixed{Overall, retrieval-augmented few-shot prompting is competitive with LoRA fine-tuning while requiring no training, and the two approaches trade different strengths. Which one suits a project depends on its labeled data, its GPU budget, and whether a missed bug or a false bug label costs it more. Our main contributions are the following:}

\begin{itemize}
  \item \fixed{\votag, a similarity-weighted $k$-nearest-neighbor baseline that measures how much label information the retrieved neighbors carry, bounds the number of in-context examples, and serves as a fallback for invalid LLM outputs.}

  \item \fixed{An evaluation of retrieval-augmented few-shot prompting (\ragtag) for \irc\ across four model sizes and seven values of $k$.}

  \item \fixed{\bragtag, a training-free retrieval intervention that reduces the question-to-bug misclassification known from prior \irc\ work, at the cost of bug recall.}

  \item \fixed{A comparison of these methods with LoRA fine-tuning of the same models on the same labeled issues, in classification performance, peak GPU memory, and labeled-data needs, reported with paired bootstrap confidence intervals and per-class precision and recall.}
\end{itemize}
